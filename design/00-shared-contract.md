## 1. Product and thesis
A coach that walks employees through deciding whether and how to automate a process, then recommends the best tool for each step. Ships as a standalone Windows download and integrates with **AutoMate** (WinUI 3 / C#, local, deterministic, **no AI at runtime**; AutomationId selectors; no coordinates; no confidence scoring for element resolution; fail loud). Never describe AutoMate itself as AI-powered; Coach is an optional design-time assistant.

**The model talks; the engine decides.** The recommendation path (classification, ladder choice, ROI math, environment fit, policy gating, exports, approvals) is a deterministic, auditable rules engine with no LLM in it. No LLM output, including an LLM judge, can change a verdict, rung, ROI figure, policy gate or approval except through a value the user accepted, and the trace shows which value that was. The model may write structured step data only as a **proposal the user confirms**; the engine consumes nothing the user has not confirmed (applies in lite mode too). One exception, ruling R4: the model may raise a Blueprint's sensitivity class (tighten only, never loosen); that applies at once, shows an undo notice and writes an audit entry.

## 2. Locked decisions (owner)
1. Coach core is a standalone library (engine, blueprint, catalog, connections, policy); AutoMate is the first "automation target" adapter; the standalone app is another shell.
2. Coach acts inside AutoMate: draft-only, user sees a diff, a single-use host-minted token from a trusted UI click approves apply/run, test runs are attended-only at first, every action maps to a Blueprint step. Nothing sends, deletes or runs without a human click. The AutoMate team owns the adapter API (draft import, diff, IPC); a file-based draft import is the fallback.
3. **Connections** (one abstraction): `managed` (customer pays platform subscription plus usage at cost + transaction fee; app to our gateway to OpenRouter), `byok_openrouter` and `byok_provider` (customer's key, called **direct from the client**, key in Credential Manager/DPAPI, never in logs, transcripts, blueprints, exports; no usage fee), `custom_openai_compat` (Azure OpenAI, LiteLLM, vLLM, corporate gateways, with a server profile), `local` (free; loopback OpenAI-compatible: Ollama, LM Studio, Foundry Local [preview], llama.cpp; servers are never bundled; no embedded inference). Local support is a launch requirement. A native Anthropic adapter is v1.1. Glossary: `byok_openrouter` means the customer's own OpenRouter API key; it is unrelated to OpenRouter's "BYOK" product.
4. **Managed is generally available only after written permission from OpenRouter (or an equivalent direct provider agreement) is on file.** Until then it ships behind a flag; BYOK and local are unaffected (OpenRouter ToS s7 bars reselling API access).
5. **Gateway privacy wording:** the gateway **does not store** prompts or completions and persists metadata only (user, model, tokens, cost, time). Prompts transit gateway memory, OpenRouter and the model provider. Copy says "not stored by us", never "we never see it". Any future in-transit scan may read content in memory and must persist counts only (P2, owner-approved exception). Managed requests always force provider data-collection deny.
6. **Tiers:** Individual, Team, Enterprise. Individual has two plans, Free (permanent, no account) and Paid; the trial is a 14-day Team organization trial; no free managed credits. Details in ruling R1 (supersedes the v2 "14-day Individual trial plus free wizard" offer).
7. **Admin and user controls at launch.** Every setting is `locked` | `default` | `user_choice`. Policy is a signed bundle (ES256 unless Ed25519 support is verified in the chosen KMS and .NET), cached with an offline grace period (default 14 days, then `no_llm`). Individual runs on a signed baseline bundle. Machine-level enrollment (registry key) ships at launch so "disable personal keys" and "org policy required" have a hard path on managed devices. Enforcement is server-side for `managed` and for approvals/retention/sharing of every synced Blueprint; client-side for direct and local connections; local-only Blueprints sit outside server enforcement and the product says so. An **org environment profile** constrains the rules engine. Single org bundle at v1 (`environment.profiles[].groupIds` is the only group-aware field; multi-group tiebreak: first profile in array order; reserve an optional `scope` field).
8. **Full blueprint backup/sync to our servers is a capability for every sensitivity class.** `restricted` Blueprints stay on the device by default, show "Local only, not backed up", and an admin or the owner may opt in with one click. Approval metadata (hash, status, signer) may sync for any class. Encryption server-managed (per-tenant KEK, per-revision DEK, AES-GCM with AAD); the envelope reserves `enc.mode`. Customer-managed keys and the Enterprise org key vault (scoped sub-key mode A only) are P2, after a security review; do not sign Enterprise contracts requiring CMK before it ships. Backup window of 35 days is stated in the DPA. One region at launch (field present). Transcripts stay local by default.
9. **Roles:** `admin`, `coe_reviewer`, `builder`, `viewer`. Admin sees Blueprint metadata plus audited break-glass content access; content is readable by the owner, explicit shares and CoE Reviewers once in review. CoE Reviewer = Builder plus review (Builder rights include AutoMate draft/apply); may not approve their own Blueprint; Admin cannot approve; only a CoE Reviewer sets `approved`. `tiers.md` section 2 is the authoritative permission matrix; `coach-tools.json` role rules are generated from it.
10. **Telemetry off everywhere** (client-reported usage is classified as audit data and the product says so). Team audit retention 365 days. Sign-in not required for local, BYOK and no-model use; account required for sync, managed and orgs; signed offline entitlement token with 30-day grace. Up to 3 devices per user. Cloud: Azure.
11. Accessibility: WCAG 2.2 AA with keyboard and screen-reader support for the shell and portal. English UI in v1 with locale-safe strings; model replies in the user's language, best effort.
12. First buyer: CoE lead. Competitors are not named on the site.

## 3. Stages, ladder, diagnostic
Stages: `triage`, `capture`, `decompose`, `classify`, `environment_fit`, `design`, `build_handoff`, `test_plan`, `deploy_monitor`. Triage verdicts: `automate`, `fix_process_first`, `dont_automate`.

**Ladder (array order = ladder order; first rung that fits wins):** `eliminate`, `builtin_feature`, `api_connector`, `script`, `ui_automation`, `parser_ocr_ml`, `llm_node`, `human_checkpoint`, `llm_agent` (discouraged: always carries a warning and a justification card; reached only where a human checkpoint is forbidden or unfit). The engine's search order, fixtures and the Blueprint enum all use this order (F-01).

Diagnostic inputs: input structure, output determined by rules, cost of error and reversibility, frequency and volume, API vs UI-only (`interfaceAvailability`: `api_available`, `file_exchange`, `ui_only`, `unknown`; steps whose systems are all `paper_or_phone` are exempt, no `none` value), attended vs unattended and credentials, data sensitivity, language understanding or judgment required, `operations` tags, plus the engine fields listed in `rules-engine.md`. Every tool-settable diagnostic field equals the schema's set (F-25).

## 4. Conventions (all JSON is camelCase)
- **Ids:** `toolId` `^[a-z][a-z0-9_]*\.[a-z0-9][a-z0-9_]*$` max 80; org tools `^org\.[a-z0-9][a-z0-9_]{0,59}$`; `slug` `^[a-z][a-z0-9_-]{1,62}$`; entity ids `bp_`, `stp_`, `exc_`, `dec_`, `tst_`, `exp_`, `aud_` + 26-char ULID; connection id `^[a-z0-9][a-z0-9_-]{0,63}$` (built-in `managed`). Both schemas define these identically (F-09, F-10).
- **Skill scale** everywhere (`skillLevel`, `builderSkill`, `prefs.skillLevel` default `basic`): `none`, `basic`, `intermediate`, `advanced`.
- **Policy three-state modes:** the refusal value is `forbidden` (never `disabled`). `user_choice` omits `value`; `locked` and `default` carry it.
- **Model keys:** `<namespace>/<id>`: managed and byok_openrouter use the OpenRouter id as is; byok_provider `<providerId>/<id>`; custom_openai_compat `custom/<id>`; local `local/<id>`.
- **Wire casing:** roles and labels are snake/lower case (`coe_reviewer`; `certified`, `works`, `experimental`, `uncertified`); display names are UI copy only.
- **Versions:** `Blueprint.schemaVersion` string `^1\.[0-9]+$` (readers preserve unknown properties, writers emit schema properties only); `Policy.schemaVersion` required integer; clients ignore unknown non-`x-` policy keys.
- **Lengths:** `flowRef` and `exportRecord.targetId` max 120 characters; override and decision reasons max 400 (policy `reasonMinChars` max 400).
- **Spend:** cap micros = round half up (USD x 1,000,000).

Migration: `spec_markdown` to (process_document, md); `spec_json` to (blueprint_json, json); `spec_pdf`/`spec_docx`/`csv` to process_document with that format; `automate_flow_draft` to (automate_flow_draft, automate_draft). Context size is probed per server kind. Never send `tools` and `response_format` together to open-weight servers.

- **ROI:** constants are placeholders; the triage ROI gate (TR-3) is advisory until the owner calibrates it from design-partner data; constants are shown in the trace. Graduation (LLM-to-code) is deferred to v1.x: keep the rule spec, collect no content.

## 6. Certification and models
Labels: `certified`, `works`, `experimental`, `uncertified`. A label belongs to a fingerprint (model, server kind, server version, quantization). Models reached through a degraded compatibility layer (for example Claude via an OpenAI-compatible layer) cap at `works`. Deterministic metrics decide labels; any LLM judge is advisory only; zero S0 runs for any model exposed to approval-class tools. Experimental models may propose but get no approval-class or AutoMate action-starting tools (users use panel buttons). Adversarial suites never run on the production gateway account; use a separate funded OpenRouter account and local models, with written approval before any red-team traffic. The `restricted` default model floor allows an admin-approved local model to count as `works`, otherwise the wizard.

### R1 Licensing (open core) and billing

Excludes sync, backup, restore, version history, device management and `managed`.
- **Individual Paid:** Free plus sync, backup (35-day window), restore, version history, up to 3 devices, and `managed` once decision 4 is met. Needs an account.
- **Team and Enterprise:** include everything in Individual Paid plus the org features in `tiers.md`, as amended by R6 to R8.
- **Trial:** 14 days of Team for a new organization (the first-buyer path), once per organization; no card at start (owner-confirmed 2026-10-26). The v2 "14-day Individual trial" is removed. When the trial ends with no subscription, members fall to Individual Free: local data untouched, synced data downloadable for 90 days, then purged (S10).
- **Billing:** platform subscription billing is live at launch and does not depend on the `managed` flag. Managed usage billing stays dark until decision 4. Payment-failure grace: 14 days (owner-confirmed 2026-10-26), then the same fall to Individual Free. Entitlement token claims: `plan` (`free|individual|team|enterprise`; Free needs no token), `trialEndsAt` (nullable), `seats`, `devices`. ### R2 Restricted data, export and handoff
- Decision 8 is unchanged: `restricted` content never uploads unless the owner or an admin opts in.
- The owner may always export locally and build a `review_packet` locally, unless the org's `data.exports.allowedKinds` excludes that kind or the class's `data.sensitivityRules[class].exportAllowed` is set to no (default yes for `restricted`). Neither action uploads anything. `sensitivityAtExport` records `restricted`.
- Review of a local-only restricted Blueprint: the owner gives the packet to a CoE Reviewer outside Coach, or opts in to sync. The packet opens **read-only and unmodified** in the reviewer's Coach, so the recomputed `contentHash` equals the owner's. The reviewer's ApprovalRecord is bound to that hash and syncs as approval metadata (decision 8). The owner's client applies the record only when its local `contentHash` matches.
- An approval-required gate is any value of `governance.approval.requiredBefore` (`build_handoff`, `handoff_brief`, `automate_flow_draft`, `export`, `automate_apply`, `automate_test_run`; default `["automate_apply"]`) or a class rule `requireApprovalBeforeHandoff` (default yes for `restricted` only), which raises the gate before `handoff_brief`, `automate_flow_draft` and `automate_apply` only. `review_packet` has no gate. A gate is met by exactly one of: (a) `approved` by a CoE Reviewer for the current `contentHash`; (b) a SelfAttestation for the current `contentHash`, valid only under R7. This holds for every class including `restricted`.

### R3 Reopening imported, shared and restored Blueprints
- A Blueprint that arrived by file import, share or restore from backup or history opens for editing with `status` = `draft` and every `confirmationState` reset to `proposed`. Audit actions: one arrival action (`blueprint_imported`, `blueprint_share_received` or `blueprint_restored`) plus one `confirmations_reset` with counts. Provenance and `createdBy` are kept as received; `confirmedBy` and `confirmedAt` are cleared.
- Not a restore: a normal sync pull of a newer revision of the same Blueprint onto the same owner's own devices keeps state. ASSUMPTION: this is what the owner means; without it every device sync would reset confirmations.
- The reset changes content, so `contentHash` changes: an approval or self-attestation never transfers to a reopened copy. A review packet (R2) opens read-only and is not reset.
- Re-confirmation: **engine-read fields** (every `diagnostic` field, `environment.systems` tool-settable fields, `triage.answers`, `process.frequency`, `process.volume`, `process.timePerRunMinutes`, `process.people`, `sensitivity`) are confirmed value by value; **free-text entities** (step name and description, exception text, process summary) are confirmed per entity ("keep this step", "keep this exception"). The engine ignores unconfirmed values, as before.

### R4 Model may tighten sensitivity, never loosen
- Coach exposes a tool that lets the model raise the class along `public < internal < confidential < restricted`. The host rejects any call that would keep or lower the class (error `sensitivity_not_tightening`). An accepted call applies at once with no chip, shows an undo notice in chat and the panel, and writes audit `sensitivity_tightened` (details: from, to, turnId). Undo restores the previous class and writes `sensitivity_changed`.
- Lowering is a panel action by the owner only, audited as `sensitivity_changed`, subject to `data.sensitivityRules`.
- The engine reads the new class at once; routing (`toolDataFlowCeiling`, model floor) applies from the next model call. A raise to `restricted` makes the Blueprint local-only; see S4 for already-synced revisions.

### R5 Chip budget (confirmation fatigue)
- **Closed-choice fields** (every closed-choice field the engine reads: triage and diagnostic enums, rule status, system enums, access modes, builder skill, owned tools; see S12) are asked in chat and answered with **host-rendered option controls**; choosing a control is the confirmation. This is the main path and produces no chip.
- **Chips** (proposal queue) are used only for values the model extracts from the user's free text (names, descriptions, system names, quotes). The host caps pending chips per turn; ASSUMPTION: the coach agent sets the number.
- **Capability tags:** a host-generated checklist of the 36-tag enum that the user ticks. The model may highlight suggestions in the checklist (never pre-ticked) and may not place chips for tags.
- **No key-repeat, no auto-advance:** a held or repeated key never accepts more than one control or chip; accepting never moves the stage or the focus on its own.
- **Read-back:** before a stage advance the host shows a read-back of the values confirmed in that stage; the advance needs a click on it.
- **`llmJustification.whyNotCode`** is written or edited by the user. The model may draft; the host stores the field only after the user has typed or edited text, with `provenance.origin` = `user_stated`. The engine treats a `whyNotCode` without `user_stated` provenance as not provided.

### R6 Break-glass
- Time box 4 hours (ASSUMPTION; policy owns the setting and may allow shorter, never longer). Access ends automatically at expiry and every read is logged. A reason is required.
- The Blueprint owner is notified when break-glass starts, naming the admin and the reason. Fixed, not a setting.
- Team: a single Admin may grant themselves access (audited, owner notified). Enterprise: a **second Admin** must approve; with only one Admin the request fails closed.
- Portal audit event names: `break_glass_requested`, `break_glass_approved`, `break_glass_read`, `break_glass_expired`.

### R7 Small teams and Viewers
- A Team with exactly one billable seat (Admin, CoE Reviewer or Builder) may record a SelfAttestation to meet an approval-required gate, as Individual does (label "self-attested", never `approved`). When a second billable member joins, approval-required gates need a CoE Reviewer again and earlier self-attestations stop satisfying them. Enterprise never accepts self-attestation. A Team that reports 0 billable seats is refused (fail closed). Where self-attestation is eligible, a reviewer's rejection does not veto it (there is no second reviewer by definition).
- Viewer seats are free and not billed. Viewers cannot spend model budget, export or approve (unchanged).
